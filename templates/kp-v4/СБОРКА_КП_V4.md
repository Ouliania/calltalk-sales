# Сборка коммерческого предложения Call-Talk V4

**Статус:** инструкция к V4 в ветке `feat/kp-v4` и PR #5. До утверждения и merge не заменяет рабочий стандарт V3 в `main`.

**Эталон:** `templates/kp-v4/CALL-TALK_Эталон_КП_9_слайдов_v4.html`  
**Валидатор:** `templates/kp-v4/validate_kp_v4.py`  
**Тестовый генератор:** `templates/kp-v4/generate_test_example.py`, только для тестов, НЕ для клиентского КП.  
**Тесты:** `templates/kp-v4/test_validate_kp_v4.py`.

## 1. Сначала проверить источники и статус сделки

1. Определить точного клиента и последнюю явную просьбу, целевые продукты, кому продаем, критерий оплачиваемого результата и следующий шаг. Использовать весь доступный контекст именно этой сделки: письма, CRM, бриф, запись и приложения. Не переносить условия других клиентов.
2. Сверить `00_АКТУАЛЬНЫЕ_УСЛОВИЯ_CALLTALK.md` и более поздние согласованные коммерческие условия.
3. Подтвердить, есть ли обязательные индивидуальные условия: стоимость лида, формат квалификации, срок, фикс, рассрочка, праздничная пауза, дополнительные ящики.
4. Недостающие критически важные сведения спросить **до финального клиентского КП**. Если вопрос не влияет на составление черновика, не тормозить работу.
5. Найти подтвержденный кейс в `БИБЛИОТЕКА_КЕЙСОВ_CALLTALK.md`. На слайде 4 всегда один кейс, все его показатели должны относиться к **одному и тому же проекту**.

**Приоритет:** новое явное согласование пользователя > подтвержденные договоренности сделки > актуальные условия Call-Talk > правила активной версии шаблона/валидатора > исторические примеры.

## 2. Выбрать режим сравнения до расчета

В HTML всегда **два тарифных блока на слайде 5 и две финансовые модели на слайдах 6–7**.

### `terms`: сравнение сроков

- Вариант 1 слева на слайде 5: стандартный срок **4 месяца** и фикс **39 000 руб./мес**.
- Вариант 2 справа: тестовый срок **2 месяца** и фикс **56 000 руб./мес**.
- Слайд 7 иллюстрирует вариант 1, слайд 6 вариант 2. Это намеренно.
- Цена лида согласовывается под конкретную сделку. Не копировать чужую.
- Не выдавать 63–94/25–42 или другие исторические прогнозы за универсальные: расчет зависит от охвата и допущений.

### `qualification`: сравнение двух форматов лидов

- **Один документ**, а не два КП.
- Две карточки на слайде 5: например, **лид с подтвержденным интересом** и **углубленно квалифицированный диалог**.
- Стоимость, требуемые сведения и оплачиваемое событие каждого формата записывать отдельно.
- В двух карточках допустим одинаковый срок и фикс, разные ставки за оплачиваемый результат.
- На слайдах 6 и 7 показывать экономику соответствующего варианта; не подписывать их «тариф 2 месяца / тариф 4 месяца», если речь о глубине квалификации.
- Нельзя автоматически приравнивать 10 заинтересованных лидов к 10 квалифицированным встречам. Каждый прогноз обосновывать отдельно.
- Если критерий квалификации включает задачу, бюджет и назначенную встречу/предметный диалог, обязательно проверять, что эти требования реально согласованы.

## 3. Рассчитать рынок, а не заменить оценку красивым текстом

Слайд 2 сохраняет **ровно пять** строк сегментов + итог, четыре столбца, две нижние карточки.

- Выбрать пять не пересекающихся настолько, насколько возможно, сегментов, для каждого назвать задачу и ОКВЭД.
- Число организаций обосновывать статистикой, реестрами, фильтрами, проверенными оценками; записать источник, дату, географию и фильтры во внутреннюю рабочую заметку.
- Проверить сумму пяти чисел. Исключить явные дубли сегментов.
- Не заменять столбец «Организаций в РФ» субъективным приоритетом.
- Без достаточной основы для оценки оставить внутренний черновик, не отправлять неподтвержденное число клиенту.

## 4. Рассчитать коммерческие показатели

Создать клиентский JSON для `validate_kp_v4.py --config` с полями:

```json
{
  "client": "Название клиента",
  "mode": "terms",
  "boxes": 10,
  "touches": 3,
  "avg_check_rub": 2000000,
  "conversion": 0.15,
  "margin": 0.15,
  "variants": [
    {
      "months": 4,
      "monthly_fixed_rub": 39000,
      "lead_price_rub": 4800,
      "leads_calc": 60,
      "periods": [
        {"contacts": 600, "rate_low": 0.01, "rate_high": 0.02},
        {"contacts": 4500, "rate_low": 0.01, "rate_high": 0.02}
      ]
    },
    {
      "months": 2,
      "monthly_fixed_rub": 56000,
      "lead_price_rub": 4800,
      "leads_calc": 30,
      "periods": [
        {"contacts": 600, "rate_low": 0.01, "rate_high": 0.02},
        {"contacts": 1500, "rate_low": 0.01, "rate_high": 0.02}
      ]
    }
  ]
}
```

**Этот JSON показывает структуру, а не реальные данные или готовый расчет.** Числа лида `leads_calc` надо выбрать **внутри рассчитанного диапазона**; приведенный пример не является заведомо согласованным. Для проверки используйте генератор тестовых файлов и его JSON, но **не отправляйте синтетическое КП**.

Расчеты на каждый вариант:
- `contacts = contacts_period_1 + contacts_period_2`;
- `emails = contacts × touches`;
- `lead_range = sum(round(contacts_period × rate_low / rate_high))`;
- `fixed = months × monthly_fixed_rub`;
- `budget = fixed + leads_calc × lead_price_rub`;
- `deals = leads_calc × conversion`;
- `revenue = deals × avg_check_rub`;
- `profit = revenue × margin - budget`;
- `payback_deal = ceil(budget / (avg_check_rub × margin))`.

Конверсия 15% и маржа 15% **только стандартные сценарные значения**, не факты о клиенте. Если есть проверенная маржа/конверсия клиента, использовать ее. Отклонения вызывают WARN, неверная арифметика всегда BLOCK. Не подбирать цену или допущения ради красивой окупаемости.

**Важно:** для варианта с квалифицированными диалогами ставка отклика может быть ниже. Использовать отдельный диапазон, если он обоснован, и не обещать, что объем результатов совпадет с обычными заинтересованными лидами.

## 5. Заполнить шаблон без перестройки макета

1. Скопировать HTML **из правильной папки** `templates/kp-v4`, а не `КП/CALL-TALK_КП_Шаблон.html`.
2. Заполнять только предназначенные `{{ПОЛЯ}}`. Дублирующиеся значения должны быть **одинаковыми** во всех слайдах.
3. Сохранять исходные CSS, HTML-узлы, классы, число блоков, размеры, логотип, контакты и весь постоянный текст. При потребности изменить постоянный текст сначала согласовать изменение эталона/валидатора, **не обходить проверку**.
4. 1: клиент и продукт; 2: пять сегментов/рынок; 3: реальные персональные цепочки; 4: один подтвержденный кейс и три причины доверия; 5: два сравниваемых предложения и критерий оплаты; 6–7: экономика двух вариантов; 8: четыре этапа запуска; 9: следующий шаг и контакты.
5. Стандартный старт: **10 почтовых ящиков**. 20/30 ящиков допускаются **только по согласованию** и вызывают WARN; объемы пересчитать, а не оставлять числа от десяти ящиков.
6. Дома/ящики и их покупка не входят в фикс, если нет отдельно согласованного исключения. Не обещать бесплатную техническую настройку за счет Call-Talk.
7. Не писать MQL/SQL в клиентском КП; вместо них конкретные русские критерии передачи и оплаты.
8. Не создавать для клиента неподтвержденные гарантии числа лидов, выручки, прибыли или продаж.
9. Не перегружать клиентский текст служебными пояснениями: «расчет:», «0 руб.», «по нашим оценкам», «не является гарантией», «три касания в скобках в каждой строке» и подобными пометками без содержательной необходимости. На слайде 5 «3 касания» пока сохранены как часть подтвержденного эталона V4.

## 6. Запустить валидатор и обработать каждый результат

```bash
python templates/kp-v4/validate_kp_v4.py --template templates/kp-v4/CALL-TALK_Эталон_КП_9_слайдов_v4.html

python templates/kp-v4/validate_kp_v4.py \
  --ready path/to/client.html \
  --config path/to/client.json \
  --client "Название клиента"

python -m unittest -v templates/kp-v4/test_validate_kp_v4.py
```

- **BLOCK:** исправить до отправки: сломанный макет, неверные суммы, запрещенные обороты и посторонние источники в клиентском тексте, незаполненные поля, расхождения JSON/HTML. Само изменение постоянной фразы не BLOCK, но проверяется отдельно. Отчет показывает ID, номер слайда, исходный текст, причину и действие.
- **WARN:** измененная постоянная фраза или нестандартное решение, требует ручной оценки: 20/30 ящиков, срок 1 месяц, другие сроки/фикс, конверсия/маржа, оговорка. Не превращать WARN в BLOCK автоматически. Для согласованного изменения использовать отдельный ID из JSON-отчета, не отключать все предупреждения.
- **OK:** автоматические проверки пройдены. Не означает, что рыночные числа/кейсы/обязательства подтверждены или верстка визуально безупречна.
- Не изменять валидатор, чтобы сделать некорректное КП «зеленым». Если бизнес-правило действительно устарело, исправлять **эталон + правило + тест + документацию** отдельным согласованным изменением.

### 6.1. Отчет по каждому замечанию

Запуск с формированием машинного отчета:

```bash
python templates/kp-v4/validate_kp_v4.py --ready client.html --config client.json --report-json report.json
```

Для каждого пункта показать пользователю **номер слайда, обнаруженный текст, ожидаемое значение, причину, действие, статус**. Не обобщать разные замечания в «не прошел валидатор». Продолжать проверку после первого сбоя, чтобы собрать максимально полный список. Финансовые ошибки всегда BLOCK независимо от согласования иных формулировок.

Чтобы адресно подтвердить уже согласованный текст или коммерческое отклонение, взять точный ID из `report.json` и сохранить в `approvals.json`:

```json
{ "approved": ["COPY-EDIT-S06-xxxxxxxxx"] }
```

```bash
python templates/kp-v4/validate_kp_v4.py --ready client.html --config client.json --approvals approvals.json --report-json final-report.json
```

Это разрешено только для `reviewable=true`. BLOCK нельзя разрешить одним ID. Не распознавать одно согласование как согласие с остальными пунктами. Если текст замечания изменился, ID изменится и потребуется новое решение.

## 7. Визуальный QA и согласование

- Открыть **настоящий HTML** в Chromium/Chrome, сделать снимки **каждого из девяти слайдов**. Проверить горизонтальные и вертикальные переполнения, перенос цифр, таблиц, подписи, читаемость текста и пропорции.
- При проблемах сначала сокращать текст внутри разрешенного поля. **Не подменять фирменный макет самодельным, похожим на него.**
- Показать пользователю HTML и по необходимости реальные браузерные скриншоты, а также краткий diff по данным и условиям. Не выдавать картинку, созданную генератором изображений, за скриншот.
- **PDF делать только после явного утверждения HTML.**
- Договор, спецусловия, праздничная пауза и что считается оплачиваемым результатом должны быть согласованы отдельно и отражены одинаково в КП и договоре.
- До merge PR #5 версия V4 имеет статус **на ревью**, и для клиентских КП нужно явно подтвердить использование этой версии.

## 8. Финальный контроль

Перед отправкой положительный ответ на 9 вопросов: правильный клиент; целевой рынок; реальные адресаты; один подтвержденный кейс; валидный результат; верная цена/фикс; согласованные предпосылки; точный расчет; понятное следующее действие. Плюс отсутствие ошибок BLOCK, обработанные WARN и просмотр всех девяти слайдов.
